# 快速交付模式：1个总控＋3个开发

生效请求：2026-09-06，用户要求加速完成。当前目标是先完成可验证的核心演示闭环，再提高完整产品评分。本模式优先于GROK_LOOP中“整个项目每轮只做一项”的串行安排；安全、授权和证据要求保留。

## 1. 并行数量与职责

启动上限为**4个Grok角色：现有总控＋3个开发子代理**，不是4个新总控。先查当前已运行的agent，复用符合分工的角色；达到上限就不继续增加。没有原生子代理能力时如实记录，不能把三段串行回答标成并行。

| 角色 | 唯一职责与文件所有权 | 本次交付 |
|---|---|---|
| 总控／产品经理／Checker | 需求、分工、接口约定、验收、状态、评分、整合提交；不与子代理同时写业务文件 | 选最短关键路径，检查3条线结果，统一跑一次集成回归 |
| A：后端与语音 | `brain/app/main.py`、`media.py`及协议／音频测试；如改动作broker先声明文件 | 取消／迟到结果、礼貌语音异常恢复；接入C提供的明确接口 |
| B：固件与本体 | `firmware/xiaozhi-niulai/`与已确认native对应文件；固件构建目录独占 | 冻结抢占、妈妈顺序、离线素材交接；源码／构建／实机分开 |
| C：角色体验与记忆 | `brain/app/secret_life.py`、`memory.py`、`origin.py`及对应测试；不得改main.py | 完成现有独处冷却／记忆接续的正向与负向验收，不造新引擎 |

`lifecycle.py`、`mcp_broker.py`等未在表中唯一指派的共享文件，由总控在第一轮明确交给一人。跨线依赖先约定函数签名／事件格式和示例，生产者做实现，调用方由A接线；其他人只提供patch建议，不能同时抢写main.py。

总控是独立Checker，须读实际diff和原始测试日志。若总控亲自修改业务逻辑，改动的检查交给没参与该段的子代理；不得自批。

## 2. 先保护正在完成的工作

当前Grok已经运行、工作区有多处未提交改动；不重新启动整个任务，不把未完成代码退回旧HEAD。

当前正在修NIU-L02的原写者优先保留为A；B/C先领确定无人修改的文件，不抢其未提交工作。由当前唯一写者停在可恢复边界后，记录HEAD、暂存区和未提交文件。再向3个子代理分配互不重叠路径；能可靠创建包含本次必要改动的隔离工作区时采用隔离，否则严格执行共享目录路径所有权。不要只从旧HEAD建三个worktree而漏掉现役新代码。

创建快照只包含所需源码与测试，不复制密钥、现役数据库、语音私人数据或原生构建缓存。活跃代码发生变化时按受测版本验证，不能复用旧63-pass结论。

所有改动由总控顺序整合；只有一个角色拥有native构建目录。测试会共享数据库／路径时先隔离，不让3套pytest同时触碰同一存储。不接管其他会话的uvicorn，不新增第二个开发scheduler。

## 3. 先交付什么，暂缓什么

本次优先完成：**妈妈→礼貌对话→靠近收住动作与秘密声音→离开后已有独处表现→断链后本地回退**，同时保留已接入的有限记忆能力。

- 已有功能先验证，缺哪段补哪段。P0-5若已由当前提交完成，不重新设计冷却器。
- 微信ClawBot保留既有适配器和离线测试；扫码／凭据未就绪时记外部依赖，不占住核心演示关键路径，也不能假报已接通。
- 暂缓全站重设计、新场景引擎、新传感器、第二块板、完整四足运动和无关重构。
- 不反复写新PRD、长日报或完整40项评分。产品经理每次只用3行给出“这轮用户可见改变／验收／不做什么”。
- 80分仍是完整产品目标。**核心演示内部联调**和**80分整体验收**分别记录，不能为了赶分拖住首个有效闭环，也不能因联调可用就宣称全部达标。原关键安全门禁、实际体验待测项目不降低、不删除。

## 4. 更短的工作节奏

1. 前5–10分钟：总控核对当前进度，只分配3个独立缺口并锁定接口；能读代码解决的细节不开展长需求讨论。
2. 每个开发者用10–15分钟交一个可检查增量；完成立即交回，不等待20分钟定时点，不为了凑时间继续改。
3. 子代理只跑自己改动对应的测试，汇报路径／diff／命令退出码／证据／待测部分。
4. 总控在有可集成增量时顺序整合，统一跑一次相关完整回归；没有新变更不重复整套测试。每30–45分钟争取形成一个可核验集成快照，这是冲刺目标，不是完成时限承诺。
5. 任一线卡住超过10分钟，立即报告具体依赖，转做该线可独立验证部分；同一错误仍最多3次有依据尝试。不能让其他两线一起等待。
6. 一条线结束后优先帮助检查另一条线的成品，再领新任务；没有真正独立任务时降到2–3个角色，禁止开空转agent。

固件构建、真实接线、设备播放与录像依然可能是串行瓶颈。更多Agent不能缩短硬件动作本身；提前准备验证步骤与证据记录，让现场操作一次覆盖多个已完成子项。

## 5. 评分与汇报不占开发关键路径

仍按固定SCORECARD，每3个**已集成成功切片**或一个可演示里程碑复评一次，不按每个子代理的内部回合复评。先看有变化的分项；没有变化的证据可继承原版本有效范围，不能机械重审40项。

每次只报告：`本轮用户可见结果｜3条线状态｜集成验证｜当前阻塞｜评分变化/尚未复评`。不保证Agent数翻倍就速度翻倍；按实际吞吐与冲突决定是否维持4个。

建议11:30停止增加新的实现切片，剩余时间只处理回归、集成与交付证据；若用户更新截止时间，重新安排。12:00仍冻结现役交卷版本。后续改进在隔离工作区，不自动更新演示样机。停止文件／用户暂停与原权限边界继续有效。
